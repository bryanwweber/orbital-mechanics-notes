# Replace poliastro in Orbital Mechanics & Astrodynamics

## Recommendation

Use Skyfield and the checked-in JPL DE442s kernel for the Mercury example in Planetary Ephemeris. Remove the poliastro fork and the direct Astropy requirement once the example is migrated and a fresh source audit confirms that there are no other Astropy consumers. Skyfield already provides both the ephemeris and element calculations, and the Planetary Parameters table generator already uses it with the same kernel. The book's uv workspace and CI target Python 3.15.

SatKit can calculate heliocentric osculating elements and publishes Python 3.15 wheels. Its documented ephemeris reader expects JPL Linux-format binary files, while the book ships a SPICE SPK file. Adopting SatKit would require a separate data-provisioning decision or an additional SPK reader. Keep it as an option for a future migration of the table generator. [SatKit release files](https://pypi.org/project/satkit/#files), [SatKit ephemeris API](https://satkit.dev/api/jplephem/)

## Repository inventory

- [Planetary Ephemeris](../chapters/reference/planetary-ephemeris.md) is the only chapter with poliastro imports. The library example converts a timezone-aware `datetime` through Astropy, selects its `jpl` ephemeris, gets Mercury's state with `Ephem.from_body`, and obtains six elements through `Orbit.from_ephem`. It uses `Planes` to switch from equatorial to ecliptic axes and finally specifies `attractor=Sun` to change the origin. The Standish, MATLAB, and Horizons examples provide comparisons.
- The first two legacy orbit calculations pass a solar-system-barycentric state to a method that assumes its input is relative to the attractor. The example therefore uses a Sun-centered force model with barycentric position and velocity until its final calculation. In the installed Astropy 8.0.2 used during the investigation, the `jpl` alias selects DE430. The migration deliberately selects DE442s and computes both sets of elements from the same correctly centered state.
- [Planetary Parameters](../chapters/reference/planetary-parameters.md) includes checked-in MyST tables. Its [table generator](../chapters/reference/assets/generate_planetary_tables.py) uses Skyfield 1.55 as locked, DE442s, a local IERS file, and gravitational parameters from a local Horizons PCK. It samples daily from December 1849 to January 2150, uses planet-system barycenters relative to the Sun and the Moon relative to Earth, rotates states into the ecliptic of date, and uses the sum of the two bodies' gravitational parameters. The Mercury chapter example has a single epoch, fixed J2000 axes, and a Sun-only test-particle convention.
- [Project dependencies](../pyproject.toml) declare the editable poliastro workspace dependency and the `vendor/*` workspace member glob. [Submodule metadata](../.gitmodules) points to the author's fork. The lint, PR preview, and deployment checkouts fetch submodules recursively. Upstream poliastro was archived in October 2023. [Upstream archival announcement](https://github.com/poliastro/poliastro/issues/1640)

### SatKit as a replacement for Skyfield and Astropy

- **Mercury example.** Use `satkit.time` with the existing UTC instant, query `satkit.jplephem.barycentric_state` for Mercury and the Sun at that instant, and subtract both position and velocity. SatKit uses meters, meters per second, and radians. Rotate the two vectors by the same fixed IAU 1976 obliquity about the ICRF x-axis for the J2000 ecliptic case. Pass the solar GM explicitly in m³/s² to `satkit.kepler.from_pv`, which defaults to Earth's GM. Read the six resulting elements and convert to the book's display units. The conversion supports Mercury's elliptical orbit. The lower-precision `satkit.planets` module implements the Standish-style approximation already taught on the page, so use the JPL API for the higher-accuracy example. [Time API](https://satkit.dev/api/time/), [JPL ephemeris API](https://satkit.dev/api/jplephem/), [Kepler API](https://satkit.dev/api/kepler/), [Planetary approximations](https://satkit.dev/api/planets/)
- **Data and packaging.** SatKit 0.24.3 publishes CPython 3.15 wheels for glibc Linux x86-64 and ARM64, Apple silicon, and Windows x86-64. Intel Macs require a source build or a conda-forge package. The JPL reader selects a Linux-format binary and caches it on first use in the process. A clean installation can download about 102 MB of DE440 on the first ephemeris query. A SatKit-only design would need a compatible, pinned local data file provisioned explicitly through `SATKIT_JPLEPHEM_FILE` and verified with `SATKIT_OFFLINE=1`. Document the model, coverage, origin, source, checksum, and install procedure. Keeping the existing SPK would require a reader such as direct jplephem, Astropy, or SpiceyPy alongside SatKit. [Release files](https://pypi.org/project/satkit/#files), [Installation platforms](https://satkit.dev/getting-started/installation/), [Data directories and offline settings](https://satkit.dev/getting-started/datadirs/)
- **Planetary Parameters generator.** Removing Skyfield would require porting its remaining consumer. Validate each planet-system barycenter, the Moon relative to Earth, and Earth-Moon barycenter separately. Preserve the table generator's daily date semantics, combined-body GM, ecliptic-of-date orientation, angle and unit conventions, and aggregation. SatKit's frame documentation distinguishes ICRF from its EME2000 frame, and the table generator needs the time-dependent ecliptic of date. Reproducing that rotation needs its own comparison. SatKit's `kepler.from_pv` takes one three-component position and velocity at a time. Prototype state sampling and measure runtime over the full date range before adopting a scalar element loop. [SatKit coordinate frames](https://satkit.dev/tutorials/Coordinate%20Frames/), [SatKit Kepler conversion](https://satkit.dev/api/kepler/#satkit.kepler.from_pv)
- **Adoption criteria.** In a separate, approved spike, install the pinned SatKit wheel on Python 3.15 and verify offline execution with an empty user data directory and pre-provisioned ephemeris. Compare states and elements for both Mercury frames against an independent same-model reference. For the table generator, compare a sample of daily states and angles, boundary dates, and every regenerated table row against the Skyfield baseline. Document intended changes due to kernel, time, or frame conventions and confirm acceptable full-range runtime before proposing removal of Skyfield. The SatKit assessment is based on its documented API and release artifacts.

## Migration steps

If the legacy DE430 kernel is cached, capture the existing chapter output with the epoch, source kernel, axes, origin, and solar GM. Use the old output to explain changes in conventions and use the same-kernel comparisons below for numerical acceptance.
2. **Preserve the instant and use local data.** Keep `T_eph` at 2020-12-08 21:30:00 UTC. Create a Skyfield time with `load.timescale(builtin=True).from_datetime(T_eph)`. Use `load_file` with `assets/de442s.bsp` from the chapter directory or `chapters/reference/assets/de442s.bsp` from the repository root. Check the candidate paths so the checkout directory can have any name. Report the expected asset if both paths are missing. Sample the state inside a `try/finally` and close the kernel there. Explain where readers running the cells separately can obtain the same file. Keep the Gregorian Julian-date calculation for Standish and label the ephemeris epoch separately as JD about `2459192.396634065` TDB. [Skyfield time API](https://rhodesmill.org/skyfield/api-time.html), [NAIF planetary kernels](https://naif.jpl.nasa.gov/pub/naif/generic_kernels/spk/planets/)
3. **Show the origin change explicitly.** Sample Mercury and the Sun at the same instant. Show that subtracting both of the Sun's barycentric vectors gives the geometric Sun-relative state, represented by `(mercury - sun).at(t)`. Display the origin change with state vectors. Compute elements from the Sun-centered state.
4. **Show the frame change with the same state.** Call `osculating_elements_of` first with its default ICRF equatorial axes, then with `ecliptic_J2000_frame.rotation_at(t)`. The fixed J2000 ecliptic rotation applies to both position and velocity. Pass `gm_km3_s2=132712440041.253311` to preserve the Sun-only test-particle convention with the DE442 solar GM. Print semimajor axis in kilometers, dimensionless eccentricity, and inclination, ascending-node longitude, argument of perihelion, and true anomaly in degrees. Wrap periodic angles to `[0°, 360°)`. Explain why the orientation angles change while semimajor axis, eccentricity, and true anomaly stay fixed. Link to the state-vector derivation and compare the ecliptic values to the Standish approximation. [Skyfield elements](https://rhodesmill.org/skyfield/elements.html), [DE442 GM](https://naif.jpl.nasa.gov/pub/naif/generic_kernels/spk/planets/de442_tech-comments.txt), [JPL frame conventions](https://ssd.jpl.nasa.gov/horizons/manual.html)
5. **Align the comparison examples.** Replace the poliastro prose and links. Retain the MATLAB example and explain its separate ephemeris and approximate rotation. For the Horizons elements walkthrough, select Mercury center `199`, Sun center `500@10`, ICRF, the ecliptic reference plane, kilometers and seconds, and the matching TDB epoch. Reproduce the setup and results in Horizons and refresh the affected settings and output screenshots, retaining their paths and MyST figure labels. Explain differences at the precision shown using the service's reported ephemeris and GM conventions. [Horizons API](https://ssd-api.jpl.nasa.gov/doc/horizons.html), [Horizons manual](https://ssd.jpl.nasa.gov/horizons/manual.html)
6. **Update dependency metadata.** Remove the poliastro requirement, workspace source override, and stale comment from `pyproject.toml`. Remove the `vendor/*` workspace member and retain `plugins/render_svg`. Repeat the direct Astropy import audit and remove its direct requirement if the migrated cells were still its only consumers. Retain Skyfield and its transitive `jplephem` dependency. Regenerate `uv.lock` with Python 3.15 and without a general package upgrade. Verify that the editable poliastro package and member are gone and let uv prune packages that lose their last consumer, such as Numba and astroquery if unreferenced. [uv workspace documentation](https://docs.astral.sh/uv/concepts/projects/workspaces/)

If a rollback is needed, revert them together so the restored chapter and lock regain their matching submodule declaration.

## Verification

### Numerical baseline

A local Python 3.13 probe using the checked-in kernel and Skyfield 1.55 produced these values with the proposed DE442 solar GM. Python 3.15 book execution remains an implementation check.

| Sun-centered axes | Semimajor axis (km) | Eccentricity | Inclination (°) | Ascending node (°) | Argument of perihelion (°) | True anomaly (°) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| ICRF equatorial | 57,909,032.4975 | 0.2056371310 | 28.553180 | 10.981081 | 67.605583 | 159.929479 |
| J2000 ecliptic | 57,909,032.4975 | 0.2056371310 | 7.003698 | 48.304745 | 29.186478 | 159.929479 |

Explicit subtraction reproduced the Sun-relative state. Astropy 8.0.2, using the same file and converting the UTC instant independently, agreed within about 0.16 m in position and `1.2 × 10⁻¹⁰ km/s` in velocity. The Standish cells give about 7.00° inclination and 159.93° true anomaly at the displayed precision.
